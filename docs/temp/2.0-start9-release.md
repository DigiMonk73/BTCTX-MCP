# BitcoinTX 2.0 on Start9: the release plan (#799)

_Session 48 · P10's plan for #799, written 2026-10-27 from `2.0` at
66e3c1e4. Every fact in section 1 was read that day on GitHub or in
the code; the sources are in section 10. The lead keeps the index on

## Context

The owner wants "a very intentional step by step release plan that misses
nothing" (#799) for BitcoinTX 2.0, from `2.0` as it is today (after
v2.0.0-beta.1, 2026-10-27) to 2.0.0 promoted to Start9's Community
Registry, and hopes for Community Beta in early November. 2.0 is multiple
wallets, exchanges or accounts, per-wallet FIFO, and coin choice in
self-custody wallets. 1.x (1.2.10) is everyone's default today and what
Start9's registries carry.

This plan is what the lead ("47 · Lead · 2.0 Start9 release") turns into
issues, kickoff prompts, a board and a merge queue (AGENTS.md, "Big work").
Its authority for the release itself stays `docs/temp/2.0-accounts.md`
section 7, B10b (#358). This plan adds what has changed since B10b was
written (2026-10-16 to 2026-10-18), the beta's remaining work, every risk
to users updating, the rollout gaps, and a schedule. Where this plan
differs from B10b's text, it says so and why (section 3.3).

Each step is a checkbox, ticked on GitHub's copy of it (the step's issue);
this file is ticked only by the lead's index updates.

## 3. Rules every step keeps

### 3.1 From AGENTS.md and the lead's kickoff (#799)
- **Never a real ledger**: not the owner's BitcoinTX (8765), not their
  BitcoinTX Preview (8767), not the `bitcointx` or `bitcointx-preview` MCP
  tools. Temp databases, the reference test ledger, the golden ledger, the
  lab VM. Session NN uses ports **9NN0–9NN9** (49: 9490–9499; 60:
  9600–9609). A Mac build runs only through `desktop/run-test-build.sh`.
- Never `pkill -f` or `pgrep -f`; never System Events AppleScript. Before
  the VM starts, `ollama ps` shows no model; whoever starts it stops it and
  Silas checks (house rule 6). The VM starts only with 10% weekly left.
- Every merge into `2.0` is the lead's (decision 25): a pin at `2.0`'s tip
  pushed from a worktree with its own `.venv`; the lead's own
  `equivalence_check --against origin/2.0` on a **trial merge onto the tip**;
  `test_seed_ledger.py` and `test_independent_figures.py` for anything
  touching figures; auto-merge with `--match-head-commit`, one at a time;
  then **read `2.0`'s full-set push run before the next merge** (a pull
  request's own run is the medium set: no click-through, Docker or StartOS
  pack; #792 and #793 cost a day in beta.1).
- Sessions never turn on auto-merge: "ready: #N" on #799, and tell the lead.
- **The owner's word, said by them**: pictures and wording they see; the
  StartOS package ("merge"); every merge into `staging`, `develop` or
  `main` that this release makes; anything sent to Start9; each
  publication ("release", said directly to the publishing session: a
  relayed one doesn't count). Decisions 30 and 31 bind every text:
  "Per-wallet FIFO", and the AI connection always called optional.
- The figures rule (AGENTS.md, "Reviews"): no figure moves, the lead
  merges; a figure moves on purpose, the owner approves a plain
  before-and-after first; a figure moves by mistake, fix it.
- A bug found on the way: an issue (decision 26), and a session for it if
  the release must wait for it (AGENTS.md, "Big work"). A security problem:
  a draft advisory, never an issue.
- Every session pushes and posts at each step; plain words for the owner;
  "multiple wallets, exchanges or accounts", never "several"; never
  "close", "fix" or "resolve" right before an issue number in a commit or
  pull request; nothing personal, no figures, keys or addresses.

### 3.2 Three rules this plan adds (the lead's calls, best practice)
1. **2.0.0 ships what a beta tested.** After beta.2's gate, only the
   version pull request, the developer docs (D6, D7a), wording fixes from
   the docs read and the README's pictures go into `2.0`. A code fix found
   later means **beta.3** and its gate, not a fix straight into 2.0.0
   (owner's question 4).
2. **The freeze covers `staging` as well as `develop`**: from the last
   `develop` merge (point 1) to "BitcoinTX 2.0" merging (point 6) neither
   takes a pull request. If `staging` took 1.x work then, "develop into
   staging" after point 6 would merge 2.0 over untested changes.
   Dependabot's pull requests wait. Anything urgent means another
   `develop` merge and point 4's tests again (B10b point 1).
3. **Every VM, Mac or Docker run uses the current StartOS** (0.4.0.4 today,
   or newer) and the published 1.2.10 as "the last 1.x".

### 3.3 Where this plan differs from B10b's text (#358, 7.4)
- **Start9's changes come back by `staging`** (AGENTS.md, "Releasing": a
  branch cut from `staging`, a pull request into `staging`), not "on
  `develop`" as B10b point 1 says: `develop` takes changes only from
  `staging` since #591.
- **No fixed number of days on Community Beta**: the brief's "14 days" is
  our own habit. Decision 22: the owner calls it, and nothing sent to
  Start9 names a number of days (owner's question 6).
- **D6 and D7a may run during beta.2's run** rather than strictly after
  point 1 (2.0-docs.md, 4.5 and its question 2): `develop` has had nothing
  new since 2026-10-24, so a collision at the catch-up is unlikely and is
  the lead's to resolve. They still merge before point 2, so the release
  tests and the docs read cover them.
- **The SDK bump** (Start9's Pre-Publish Checklist, item 1) is a step of
  its own before beta.2, so a beta tests it; B10b doesn't list it.
- **New release tests** for gaps the current tracks don't cover (step 54):
  the 1.x Mac app updated in place by 2.0.0's, a Preview's backup restored
  into 2.0.0, a 2.0 connector against a 1.x server, and the Community Beta
  update itself.

## 7. The owner's decisions

One plain question each, with a recommendation and the reason. The lead
brings them to the owner; the answers go on #799.

1. **Which polish goes into 2.0.0?** (#774–#778, #651, #680)
   **Recommendation:** only the small items you pick now, in beta.2; the
   rest in 2.0.1. Each screen change is new code that testers and the
   release tests must see again, and late screen work is what moves dates.
2. **#798 (a notes field, and fee gains and income readable by the AI):
   2.0.0 or later?** **Recommendation:** after 2.0.0 (2.0.x). Nothing is
   wrong today, and new connector tools mean new tool text, guide and
   docs to check again.
3. **#649's before-and-after** (a fee added by the AI or the API without
   its currency is priced at the hour instead of the day: cents, on that
   spend only). **Recommendation:** approve it when session 50 posts it
   in plain words: the IRS rule is one price for one spend, as the form
   already does.
4. **A code fix found after the last beta: another beta first?**
   **Recommendation: yes.** 2.0.0 then ships exactly what a beta tested,
   plus its version and docs; a fix straight into 2.0.0 would be the only
   untested code in the release.
5. **When does the GitHub beta end?** **Recommendation:** once your four
   checks are done (the web view, your files, the StartOS backup way back,
   your Mempool), every beta bug is fixed, and beta.2 has run 5 days with
   no new blocker. That's about 2026-11-05, so the release run starts
   with that week's fresh usage. The longer soak happens on Community
   Beta, where StartOS users choose to test.
6. **How long on Community Beta before you ask Start9 to promote?**
   **Recommendation:** at least 14 days with no blocker, and your own
   server updated and checked. That's our own rule (decision 22): nothing
   sent to Start9 names a number of days.
7. **A 1.2.11 for #649, for people who stay on 1.x?**
   **Recommendation: no** (decision 7). It's cents on a rare path (an AI or
   API edit), fixed in 2.0.0, and a 1.x release would need its own Start9
   round in the same weeks and change the version 2.0's notes count from.
   Revisit only for a serious 1.x bug.
8. **Docker's `:latest` moves to 2.0 the day `main` moves, before Start9:
   all right?** **Recommendation: yes,** as every release does. The app
   keeps a pre-2.0 copy, the notes and README say how to stay on
   `:v1.2.10` or go back; holding `:latest` back would need a tooling
   change and leave the README's Docker steps wrong.
9. **After 2.0, keep the pre-release path (alphas, betas, the Preview
   app) for later versions?** **Recommendation:** retire it with step 60.
   It's built around the `2.0` branch; a future big version can bring it
   back by its own plan, and fewer branch rules are easier to follow.
10. **When do you update your own Mac app (your real ledger)?**
    **Recommendation:** at promotion, after Community Beta's soak, with
    BitcoinTX's own backup downloaded first: your real tax records wait
    for the most-tested build.
11. **The outside pull requests:** allow #626's CI and a review, close
    #766 (a stray file into `main`) and #562 (Grok's trial), and decide
    your own #599. **Recommendation:** yes to each; #626 has waited past
    the week CONTRIBUTING promises.
