# BitcoinTX 2.0: several wallets, exchanges and banks

The plan for 2.0 (#251), written by four planning sessions before any
code. Nothing here changes 1.x: 2.0 is built on its own `2.0` branch, and
only after Start9 promotes the 1.x stable candidate (#143).

- [x] P1 · Inventory (#252): what assumes one wallet, one exchange or one
      bank; what it means for an existing user; the IRS rules; the open
      questions (sections 1 to 4)
- [ ] P2 · Design: answers the open questions with the owner, then the
      data model, the rules per transaction type, the forms, the gate, the
      tests and the rollback of each step
- [ ] P3 · Try to break the design (a fresh Claude reviewer; Grok in Cursor)
- [ ] P4 · Build steps, one session and one pull request each; the `2.0`
      branch set up

**In plain words (P1):** BitcoinTX already keeps each of its two bitcoin
accounts, Wallet and Exchange BTC, as its own pile of coins, oldest first.
So 2.0 isn't a rewrite of the tax engine. What's fixed to "one of each" is
spread wide but shallow: the rules for which account a Buy or Sell may use,
about twenty spots that ask "is this Wallet or Exchange BTC?" by number,
the imports, the AI connector, the screens and the texts. The big risk for
someone who already uses BitcoinTX is history: moving old transactions into
a new account changes the figures of years already filed (section 2, C2).
The IRS rules (section 3) match what 2.0 wants: each wallet and each
exchange account is its own pile, first in, first out, by the date the
coins were first acquired.

**How this was made:** every claim was checked in the code on `develop`
or read from the IRS's own documents (3.1), and two claims were run on
throwaway databases on 5fb6ac5 (2, C2; 1.12). Line numbers are those of
`develop` at 3c793be (2026-10-15), which includes #283 (#279's fix of the
CSV preview's account checks, #266: the preview now refuses what the save
refuses, `USER_ACCOUNTS` included, and a transfer across currencies). Still
open when this was written: #282 (Delete All, which touches no account
check) and the issue #285 (not built yet: the preview will call the save's
own checks for fees, dates, the 21M cap and the purpose's length, with no
new account rule).

### 1.3 The engine: what is already per account

Checked in `backend/services/transaction.py`; these need no change of idea,
only the new rules above.

- **Lots belong to an account through the transaction that made them.**
  `BitcoinLot` has no account column (`models/transaction.py:292-362`); a
  lot is the account's when its creating transaction's `to_account_id` is
  that account (`_open_lots`, `:1126-1137`; the year-end holdings read it
  the same way, `services/reports/reporting_core.py:329-330`).
- **FIFO is per account, by the date first acquired.** `_open_lots` takes
  the account's lots with BTC left, ordered by `acquired_date`, then id
  (`:1135`). A Sell or Withdrawal takes from its own account's lots only
  (`maybe_dispose_lots_fifo`, `:1045-1090`, `:1077`). Seen on a throwaway
  database: 2, C2.
- **A Transfer moves lots with their date and basis.** `_LotMove`
  (`:1461-1545`) takes the amount from the source's oldest lots and makes
  new lots in the destination with each source lot's `acquired_date`,
  pro-rated basis and `inherited` flag (`add_destination_lots`,
  `:1533-1545`). The fee's part is a disposal (`dispose_fee`, `:1512-1531`).
- **A Transfer to the same account records only its fee** (#159,
  `_fee_leaving_account`, `:1449-1458`; `:1440-1441`), and needs one
  (`_enforce_fee_rules`, `:1969-1970`).
- **Most checks already go by the account's currency**, not its id: the
  ledger lines (`build_ledger_entries_for_transaction`, `:870-896`), lot
  creation (`maybe_create_bitcoin_lot`, `:1014-1016`), disposal
  (`:1055-1057`), transfers (`:1419-1423`), `_into_btc` (`:1372-1374`), the
  type requirements (`_check_type_requirements`, `:1854-1879`), the date
  originally acquired (`_takes_original_date`, `:1882-1884`; the check,
  `:1907-1923`), fee currency (`_check_fee_currency`, `:1809-1819`;
  `_fill_fee_currency`, `:1926-1946`; `_enforce_fee_rules`, `:1956-2004`;
  `_default_btc_transfer_fee`, `:1608-1617`).
- **The fee accounts are two, shared by every account** (`_fee_account`,
  `:913-915`, by name). Fees are taken from the paying account's own lots
  either way; the fee accounts only hold the fee's ledger line.
- **Balances are per account already** (`services/calculation.py:47-66`,
  every row of the accounts table).
- **The recalculation replays everything in time order**
  (`recalculate_all_transactions`, `:1548-1573`): any change to an old
  transaction can move any later figure, in any year. True in 1.x too; 2.0
  adds more ways to do it (2, C2).
- Messages that name the fixed accounts (shown to users and passed on by
  the AI): `:1415-1416` (docstring), `:1897-1898` ("…into Wallet or
  Exchange BTC."), `:2009-2028`.

## 2. Consequences for someone who already uses BitcoinTX

Each with an example. "Filed years" means tax years whose forms the user
may already have sent.

**C1. Upgrading a 1.x database changes nothing by itself.** Ids 1–6 and 99
stay (owner, #251 decision 4); lots are found through the transaction that
made them (1.3), so no lot moves. A migration adds what the accounts table
needs (a kind, the exchange pair) and fills it for ids 1–6. Test: the
reference figures and the independent check agree before and after.
Example: a 1.x ledger with Wallet and Exchange BTC lots gives the same
Form 8949 rows after the upgrade.

**C2. Moving an old transaction into another account changes filed years.**
Run on a throwaway database (`develop` 5fb6ac5), with Exchange BTC standing
in for a second wallet, which FIFO treats the same way:

| | Wallet holds | The 2024-05-01 spend of 0.5 BTC for $30,000 |
|---|---|---|
| As entered | 1 BTC from 2020-03-01 ($5,000) and 1 BTC from 2023-06-01 ($25,000) | basis $2,500, gain **$27,500, long-term** (the 2020 coins) |
| The 2020 deposit edited into another account | only the 2023 coins | basis $12,500, gain **$17,500, short-term** |

The 2024 return already filed would be wrong by both amount and term. 1.x
can do this too (edit a deposit from Wallet to Exchange BTC), but 2.0 invites
it: a user who pooled two wallets in 1.x and now adds the second one will
want to "put the old deposits where they really went". Q4, Q5.

**C3. Splitting a pooled wallet or exchange.** A 1.x user with two wallets
recorded both as Wallet (README, "One wallet, one exchange"). In 2.0, if
the new wallet starts empty and coins move into it by a Transfer dated when
they actually moved, the Transfer takes the **oldest** coins of Wallet
(FIFO), not necessarily the coins that were really in the second wallet;
past years stay as filed (pooled). Rewriting the history instead (C2)
changes filed years. Either way, figures for 2025 on (when the IRS rule
applies, 3.2) can differ from a per-wallet calculation from the start. The
app can't know which coins were where; Q5 decides what it offers and says.

**C4. Moves between two wallets or two exchanges.** In 1.x they are a
Transfer to the same account, recording only the network fee (#159: the
coins stay in their lots). In 2.0 a move between two tracked accounts is an
ordinary Transfer: the coins leave the source oldest first and keep their
dates and basis; the fee is a disposal, as today. Old same-account rows
keep their 1.x meaning unless the user edits them (C2). Example: 0.3 BTC
Wallet → Wallet with a 0.0001 fee: today a fee disposal only; in 2.0, Wallet
A → Wallet B, also 0.2999 BTC of lots move to B.

**C5. Buys and Sells on a second exchange.** A Buy takes dollars from a
bank or that exchange's own dollars and puts the coins in that exchange's
BTC account; a Sell is that exchange's BTC to its own dollars. Until
`form_8949._broker_reporting` (1.5) changes, a Sell from a second exchange
would be treated as not broker-reported (box I/L instead of H/K, or G/J
from 2026): the gain is the same, the box and Schedule D line are wrong. So
the forms change before the gate opens (P4's order).

**C6. Fees.** Unchanged in idea: a Buy's or Sell's USD fee is the trade's
(basis or proceeds); a BTC network fee is a disposal from the paying
account's oldest coins. The two fee accounts stay shared (1.3).

**C7. Income, rebates, inherited coins and gifts into a new wallet.** The
engine values them by currency (1.3), but the reports, the dashboard,
Ledger Review, the hourly check, the AI import's autofill and the CSV
export ask for ids 2 or 4 (1.4). If the gate opened first, **income into a
new wallet would be missing from the tax report and the dashboard**, and a
gift from it would keep a blank value. So 1.4 is fixed before the gate
opens.

**C8. The 2025+ boxes and covered lots, per exchange.** Today: covered
(G/J) only for a lot bought on the one exchange from 2026-01-01 and sold
there without moving. In 2.0: covered only when bought and sold in the
**same** exchange account; coins moved from exchange A to exchange B are
noncovered at B (3.5), so a Sell of them at B is H/K (proceeds only). A
user who in 1.x set `broker_reporting` to "proceeds" on such a Sell (the
guide's advice, `guide.py:142-144`) keeps that setting: it wins over the
rules (`form_8949.py:216-218`), and gives the same box.

**C9. Year-end holdings.** Already listed per lot with the account's name
(1.5): the new accounts show by name. The start-of-year list has no account
column (add it). The year-end value uses one price for every account
(unchanged).

**C10. Ledger Review.** Its checks miss new accounts until 1.4 is fixed;
its items name no account (1.6).

**C11. Backups and restore.** A 1.x backup restores into 2.0 (upgraded
first). A 2.0 backup can't be restored into 1.x (refused as newer, 1.7):
**going back from 2.0 to 1.x means restoring a backup made before the
upgrade, losing what was entered since.** The upgrade's own copy
(`<data dir>/backups/`, made by the migration) is that backup.

**C12. CSV export and re-import.** A new account exports a blank name
today (1.7). In 2.0 the export writes each account's name, and the import
reads it back; a CSV exported from 1.x (names Bank, Wallet, Exchange USD,
Exchange BTC, External) must still import (Q9). If names can be changed
(Q2), a CSV exported before a rename names an account that no longer
exists.

**C13. The AI connector.** The connector on PyPI has the five names
compiled into its tool schemas (1.8): **a 1.x connector can't name a new
account**, and its guide tells the AI to pool. A 2.0 connector must read
the accounts from the server; whether it still works with a 1.x server is
Q10. A connector installed from an older release keeps its names and its
guide until it is updated, so the server's own checks must decide, never
the connector's.

**C14. The reference test ledger and its figures.** Adding second-account
rows moves the figures of the years they're in. AGENTS.md "Testing" wants
every existing row's figures unchanged: the new rows should use only new
accounts, or move coins out of an existing account only after its last
disposal (Q18).

**C15. The StartOS package and Start9.** The store descriptions, the
instructions' Limitations and the release notes all say "one wallet, one
exchange" (1.11). 2.0's release changes them in five languages, and Start9
reviews a large change; nothing changes in the package before then.

**C16. The Mac app** holds the owner's real ledger. It upgrades the same
way (C1); the owner's own test of 2.0 must happen on a copy, never the real
data.

### 3.2 Treas. Reg. §1.1012-1(j): wallet by wallet, from 2025

- **Applies** "to all acquisitions and dispositions of digital assets on or
  after January 1, 2025" ((j)(6)). It comes from §1012(c)(1): the basis
  conventions "must be applied on an account-by-account basis" (as Rev.
  Proc. 2024-28 §2 puts it).
- **Not at a broker** ((j)(1), (j)(2): "such as in a single unhosted wallet
  or in a hosted wallet provided by a person other than a broker"): the
  taxpayer may identify the units sold on their own books "no later than
  the date and time" of the sale. Without that, units go "in order of time
  from the earliest date on which units … were acquired by the taxpayer",
  and "the date any units were transferred into the taxpayer's wallet is
  disregarded". The regulation's Example 2 applies this to the units "held
  in the unhosted wallet" only: FIFO wallet by wallet, by the date first
  acquired.
- **At a broker** ((j)(3)(i), (ii)): the taxpayer identifies units **to
  the broker** (a standing order counts; a broker with only one method
  makes it a standing order), else FIFO by the date first acquired, the
  transfer-in date disregarded. Example 4: the earliest units "held in
  TP's account with BEX", one broker account at a time. It also shows
  that the broker may report different units than the taxpayer must use
  (when the broker had no purchase dates for coins transferred in).
- **A wallet**, per §1.6045-1(a)(25): "a means of storing … a user's
  private keys"; addresses a wallet generates and "a sub-ledger account of
  a wallet" are held in that wallet ((a)(25)(iv)). FAQ Q96: a duplicate
  record of the keys "does not result in a single wallet that holds all of
  the digital assets".
- **Changing the identification method is not a change of accounting
  method** ((j)(4)).

### 3.3 Rev. Proc. 2024-28: the one-time move to wallet-by-wallet

- A **safe harbor** to allocate "unused basis" (the basis of coins still
  held) to the coins in each wallet or account **as of January 1, 2025**
  ("immediately after the close of the taxpayer's day on December 31,
  2024", §3.10). Only for coins held then (§4.01(1)–(2)).
- Two ways: a **specific unit allocation**, completed before the earlier
  of the first sale, disposition or transfer of that asset on or after
  2025-01-01 and the due date (with extensions) of the 2025 return
  (§5.02(4)); or a **global allocation**, a rule written in the taxpayer's
  books **before January 1, 2025** and completed by the later of those two
  dates (§5.02(5)). Allocations are "irrevocable" (§4.02(6)); basis
  already used can't be allocated again (§5.02(7)).
- The background (§2): many taxpayers had used a "universal or
  multi-wallet approach" before 2025, which the old FAQ didn't forbid.

### 3.4 Notices 2025-7 and 2026-20: identification for coins at a broker

Through **December 31, 2026** (Notice 2026-20, §3.03), units held at a broker
may be identified on the taxpayer's **own books** (a choice before the sale,
or a standing order written in the books), and then those are the units sold
"regardless of whether the information reported by the broker to the
taxpayer matches the taxpayer's books and records" (§4.05). Taxpayers using
Rev. Proc. 2024-28 may rely on it only after meeting its requirements
(§4.04). From 2027, identification of exchange-held coins goes to the
broker again ((j)(3)(ii)); without it, FIFO per broker account.

### 3.5 Covered lots and the broker's form (Form 1099-DA)

- **Covered** (§1.6045-1(a)(15)(i)(J)): "acquired in a customer's account
  by a broker providing custodial services … on or after January 1, 2026,
  in exchange for cash, stored-value cards, different digital assets, or
  any other property or services". The 2026 1099-DA instructions add that it
  is covered "only if it was acquired in an account for which the broker
  provided custodial services and was held in that account until the
  broker effects the disposition". **Noncovered** includes "A digital
  asset that was transferred in to the broker providing custodial
  services" and anything acquired before 2026.
- **No transfer statement is required** between brokers for digital assets
  (§1.6045A-1(a)(1)(vi)), so coins moved from one exchange to another
  arrive noncovered (the covered-by-transfer-statement route,
  §1.6045-1(a)(15)(i)(G), doesn't arise unless a broker sends one).
- **2025:** brokers report gross proceeds; "Brokers are not required to
  report basis information with respect to sales effected in 2025" (2025
  instructions, p. 1).
- **The broker's own lot order** (2026 instructions, p. 8): the customer's
  identification, else "the earliest units of the digital asset purchased
  by the customer"; without customer-provided acquisition information,
  "treat digital assets transferred into the customer's account as
  acquired as of the date and time of the transfer", and such information
  is used "solely for lot-selection purposes and not for reporting basis
  or acquisition dates". So a broker's 1099-DA can differ from the
  taxpayer's own FIFO by original dates (#158).

### 3.6 Form 8949 (2025)

- Digital assets use boxes G, H, I (short) and J, K, L (long), never C or
  F (instructions, p. 1 and p. 4); "Use a separate Part I for each type",
  "Check only one box on each Part I" (p. 3–4).
- Several brokers: the instructions ask for nothing per broker when each
  transaction is on its own row. Only Exception 2 (summary totals instead
  of rows) says "If you have statements from more than one broker, report
  the totals from each broker on a separate row" (p. 4). BitcoinTX lists
  every disposal, so it doesn't use Exception 2.
- Column (b) may say "VARIOUS" for units bought on several dates, but
  short- and long-term still go on separate parts (p. 6); "INHERITED" for
  inherited property (p. 6).

### 3.7 What this means for BitcoinTX

**Already followed by 1.x (for its two bitcoin accounts):** FIFO within
each account by the date first acquired, the transfer date disregarded
(1.3); a transferred lot keeps its date and basis; coins moved between
one's own accounts aren't sold, but the fee paid in coins is (FAQ Q81); the
2025+ boxes; covered only for coins bought on the exchange from 2026 and
never moved (1.5).

**2.0 must follow:** the same, for every wallet and every exchange account
separately; covered per exchange account (bought and sold in the same one;
moved between exchanges = noncovered); each exchange's Sells
broker-reported by that exchange; income and gifts recognized whatever the
account (1.4).

**2.0 must not promise:**

- **Choosing which coins to sell** (specific identification), in a wallet
  or at an exchange: FIFO only, as in 1.x (#251). Through 2026 a user may
  identify units on their own books (3.4), and a broker may apply a
  standing order other than FIFO; BitcoinTX's figures then differ, and
  the report should say so.
- **Tracking coins by address or UTXO.**
- **The Rev. Proc. 2024-28 allocation.** Its deadlines (3.3) have passed
  for anyone who sold or moved bitcoin in 2025, and for everyone once the
  2025 return's due date (with extensions) has; it is the taxpayer's own,
  irrevocable choice, made with a tax professional, not in the app.
  BitcoinTX's per-account lots as of 2025-01-01 are whatever its history
  gives.
- **That past years were right** for a user who pooled several wallets in
  1.x: those years used one pile for what were several wallets (README,
  "One wallet, one exchange"). Before 2025 the IRS's FIFO default (FAQ 41)
  didn't say "per wallet", and many read it as across all holdings (the
  "universal" approach, Rev. Proc. 2024-28 §2), while records per wallet
  could support identification (FAQ 40); which one a user's returns relied
  on is for their tax professional.
- **That BitcoinTX matches each 1099-DA.** Brokers may use other lot dates
  (3.5); #158 is where a broker's figures are entered.

## 4. Open questions for P2

Each has one recommendation. P2 puts them to the owner in one round.

**Q1. What is an account?** Recommendation: three kinds the user adds:
**bank** (USD), **wallet** (BTC), and **exchange**, which is always a pair,
its dollars and its bitcoin, as two rows in the accounts table tied
together (so a Buy at one exchange can't spend another's dollars). External
(99) and the two fee accounts stay as they are, internal.

**Q2. Can accounts be renamed?** Recommendation: yes, every account the
user has (Bank, Wallet and Exchange included), by a display name kept
unique ignoring case; `seed_defaults` stops resetting names of ids 1–4 (it
keeps resetting the fee accounts'). The 1.x names stay accepted by the
imports for ids 1–4 (Q9).

**Q3. Ids for new accounts.** Recommendation: new accounts start at id 100,
so 99 (External, no row) can never be taken; the migration checks for
accounts other than 1–6 already in a 1.x database (the API could create
them) and keeps them only if no transaction names them, else stops with a
plain message.

**Q4. Editing an old transaction into another account.** Recommendation:
allowed, but before it saves, the app shows what it would change in each
year (Ledger Review's `recalc_changes` already computes this) and makes a
backup copy; years that change are named in plain words.

**Q5. A user who pooled several wallets or exchanges in 1.x.**
Recommendation: a new account starts empty and gets coins by a Transfer
dated when they moved (FIFO from the source; dates and basis kept); the
app never re-assigns history by itself, and says once, when the second
wallet or exchange is added, that years before it were figured pooled and
that a tax professional can say whether anything needs amending. No
Rev. Proc. 2024-28 tool (3.7).

**Q6. Covered lots and broker reporting per exchange.** Recommendation: a
Sell from any exchange's BTC account is broker-reported by that exchange;
covered when its lot was made by a Buy into that same exchange's BTC
account on or after 2026-01-01 (moved coins are never covered); the
per-transaction `broker_reporting` override stays and wins.

**Q7. Forms and the report per account.** Recommendation: Form 8949 stays
one set of sheets per box, a row per disposal, column (a) unchanged (3.6);
the Complete Tax Report adds the account (and exchange) to each disposal
and to the start-of-year holdings, so the user can match each exchange's
1099-DA.

**Q8. The River import.** Recommendation: the import asks once per file
which exchange it is (default: the first exchange, today's Exchange) and
which wallet untagged sends and receives go to (default: the first
wallet), each row still editable in the preview.

**Q9. Accounts in CSV files.** Recommendation: keep names (the format is
for people), each account's current name on export; the import reads the
user's names ignoring case, plus the 1.x names for ids 1–4, and refuses
others with the list of valid names. A 1.x CSV imports into 2.0 unchanged.

**Q10. The AI connector.** Recommendation: the server lists the accounts
to the AI key (a read-only route added to `AI_KEY_ROUTES` on purpose, with
id, name, kind and currency); the connector checks names against it at
run time instead of a fixed list, and `get_portfolio` includes it (no new
tool, so the tool count stays 11). Against a 1.x server (no list) the
connector falls back to today's five names.

**Q11. Who adds accounts.** Recommendation: only the owner, logged in
(Settings), like the other settings; the AI key can't create, rename or
hide one. The guide tells the AI to ask the user to add a missing wallet or
exchange in BitcoinTX, never to pool it.

**Q12. Deleting and changing accounts.** Recommendation: an account no
transaction names can be deleted; one in use can only be hidden from the
pickers (its history stays); its currency and kind never change once used;
ids 1–4 can be renamed (Q2), the fee accounts can't, and none of 1–6 can
be deleted. The fee accounts' gap in 1.x (#289) is worth its small fix
now, in 1.x.

**Q13. One answer to "is it a bitcoin account?".** Recommendation: one
helper that reads the account's currency, replacing `BTC_ACCOUNTS` in all
of 1.4 (and the frontend's `id === 1 || id === 3`), done before the gate
opens.

**Q14. Transfers between any two accounts.** Recommendation: any two of
the user's accounts in the same currency (bank to bank, one exchange's
dollars to another's, wallet to wallet, exchange to wallet and back); a
Transfer to the same account stays only for a BTC account's consolidation.

**Q15. Buys.** Recommendation: a Buy is paid from a bank or from that same
exchange's dollars, and lands in that exchange's BTC account; a Buy paying
with one exchange's dollars into another's bitcoin is refused.

**Q16. The dashboard.** Recommendation: one row per account, an exchange's
dollars and bitcoin together, and today's totals (total BTC, average cost,
gains) unchanged.

**Q17. Order of the build.** Recommendation: data model and migration;
then 1.4 and the forms (1.5) made general and tested with the gate still
closed; then the imports, export and connector; then the gate; then the
screens; then the texts (1.11). Each step leaves 1.x users' figures
unchanged (the reference figures and the independent check).

**Q18. Test data.** Recommendation: make `scripts/independent_figures.py`
general (a pile per account, covered per exchange) before the engine
changes; then add rows to `testdata/reference_ledger.json` that use new
accounts only, or that move coins out of an existing account only after
its last disposal there, so every existing row's figures stay the same
(AGENTS.md "Testing").

**Q19. What a wallet is.** Recommendation: the user decides; the help text
gives the IRS's meaning (3.2: one set of keys, its addresses included) and
says that a backup of the same keys isn't a second wallet.

**Q20. What 1.x users see after upgrading.** Recommendation: the same
three accounts and the same figures; the About notice changes from "one
wallet, one exchange" to how to add one, with Q5's note about years
figured pooled.
